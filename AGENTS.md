# Инструкции AI-ассистентам

## Ветки и начало работы

1. Прочитай README.md и CONTRIBUTING.md. Уточни задачу и критерии приёмки.
2. Проверь `git status`, `git remote -v`, `git branch -vv`, `git worktree list` и `gh auth status`. Определи исходный репозиторий, fork и GitHub-логин разработчика. Не используй общий корпоративный аккаунт.
3. На удалённом репозитории у разработчика **одна постоянная рабочая ветка `<github-login>`**, например `ivan`. Системные `dev` и `master` к этому ограничению не относятся. В fork действует то же правило для рабочих веток; служебные копии dev/master не являются дополнительными рабочими ветками.
4. Сначала `git fetch` исходного репозитория и своего origin. Если ветка пользователя есть на origin, используй её через tracking branch, а не создавай заново от dev. Если она есть локально — используй её, предварительно учитывая изменения с origin через обычный merge. Если нет нигде — создай один раз от актуального удалённого dev. Затем влей актуальный dev обычным merge. При расхождении историй разбери причины, ничего не перезаписывай.
5. Не создавай ветки на задачи, AI-сессии и эксперименты на GitHub. Для временной локальной ветки/worktree нужна реальная необходимость; их нельзя автоматически публиковать.

## Что хранить в Git

- Исходный код, необходимые конфигурации без секретов, manifests и lock-файлы зависимостей, поддерживаемые тесты и обезличенные fixtures.
- Готовые, проверенные и используемые сайтом ассеты в каталоге проекта, например `public/assets/` или `src/assets/`. Временные варианты туда не класть.
- Итоговую документацию проекта и командные инструкции: README.md, AGENTS.md, CONTRIBUTING.md и регламент владельца.

## Что оставлять локально

- Секреты, `.env`, токены, ключи, реальные клиентские данные, выгрузки баз и приватные документы. Чувствительные материалы по возможности держи вообще вне репозитория; внутри — только в игнорируемом локальном каталоге. `.env.example` содержит только пустые или вымышленные значения.
- Брейншторминг, планы AI, логи диалогов, промежуточные отчёты, промпты и служебные артефакты нейронок. Храни их в `work/`, `.ai/` или `artifacts/`, а не в отслеживаемой документации. Не коммить `docs/superpowers/`.
- Пробные картинки, скриншоты проверок, варианты генераций, исходные загрузки и временные экспорты — в игнорируемых каталогах. В Git переносится только выбранный готовый ассет; не игнорируй все PNG/JPG/SVG целиком.
- Зависимости, сборки, кэши, временные файлы, локальные настройки IDE, локальные worktree.

До создания локального артефакта выбери игнорируемый путь. При новом типе мусора дополни .gitignore точным правилом. Не скрывай исходники, тесты, конфигурацию или готовые ассеты общим шаблоном.

`.gitignore` не защищает секреты и не исключает уже отслеживаемые файлы. Проверь `git ls-files -- <path>` и `git check-ignore -v --no-index -- <path>`. Если файл уже отслеживается, обсуди снятие с учёта через `git rm --cached -- <точный путь>`; не удаляй локальные данные и не переписывай историю самостоятельно. При утечке секрета останови push, сообщи владельцу: секрет нужно отозвать/заменить, одного gitignore недостаточно. Не цитируй секрет в отчётах.

## Перед каждым push

1. Проверь `git status --short --untracked-files=all`, `git diff`, `git diff --cached`, `git diff --check` и список файлов всех исходящих коммитов (`git diff --name-status origin/<login>...HEAD`, если удалённая ветка существует). Убедись, что нет мусора, секретов и файлов вне задачи. Gitignore не отменяет проверки содержимого.
2. Добавляй файлы явно по путям. Не используй без разбора `git add .`, `git add -A` и `git add -f`.
3. Получи свежие origin/<login> и dev исходного репозитория, влей изменения обычным merge и повтори реальные проверки проекта. Не выдумывай успешные тесты, если приложения и CI ещё нет.
4. Проверь `git branch -vv` и `git worktree list`. Убери только свои временные worktree и локальные ветки, чья работа уже сохранена и полностью влита. Перед удалением проверь status, включая untracked и ignored файлы, outgoing commits и предназначение worktree. При любой несохранённой работе или неясности оставь их и сообщи человеку. Не удаляй чужие ресурсы, постоянную пользовательскую ветку, dev или master.
5. Для подтверждённо ненужного чистого worktree используй обычный `git worktree remove <точный путь>`, без force. Для влитой временной ветки — `git branch -d <имя>`. Отказ команды — причина остановиться, не повод добавлять force. Не используй `git clean`, `reset --hard`, `branch -D`, `worktree remove --force`, массовые удаления и стирание папок worktree вручную.
6. Посмотри ветки на origin (`git ls-remote --heads origin`). Не удаляй удалённые ветки без отдельного разрешения владельца и не трогай чужие. Лишние старые ветки перечисли человеку. Не используй push --all, --mirror или --tags.
7. Push только явной своей ветки: `git push -u origin <github-login>`. Не пушь из временной локальной ветки и не меняй dev/master напрямую. Force push запрещён.

## Завершение

Создай или обнови PR `<github-login> → dev` исходного репозитория. Для одной ветки не создавай дублирующие открытые PR. Сливай только по поручению человека, при наличии прав и выполненных требованиях GitHub. Применяй **merge commit**, чтобы сохранялась общая история постоянной ветки; squash/rebase merge не использовать.

После слияния не удаляй ветку пользователя. На чистой рабочей копии обнови локальную dev через pull --ff-only от исходного репозитория и проверь общую версию. Затем вернись в постоянную ветку, влей свежий dev и при необходимости запушь её обычным push. На другом устройстве сначала получи и влей изменения постоянной ветки с origin. Незавершённые изменения сохраняй и обсуждай, не стирай ради переключения.

Настройки доступа и защиты, теги, GitHub Releases, master и деплой меняются только по отдельному явному поручению владельца. PR в dev не является разрешением на production.
