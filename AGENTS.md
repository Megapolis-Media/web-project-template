# Инструкции AI-ассистентам

## Ветки и начало работы

1. Прочитай README.md и CONTRIBUTING.md. Уточни задачу и критерии приёмки.
2. Проверь `git status`, `git remote -v`, `git branch -vv`, `git worktree list` и `gh auth status`. Определи исходный репозиторий, fork и GitHub-логин разработчика. Не используй общий корпоративный аккаунт.
3. **Для команды единая рабочая ветка — `dev`.** Проверь действующий GitHub-аккаунт, принятый Write-доступ и персональное исключение из обязательного PR в действующем ruleset. При работе над самим шаблоном проверь правила шаблонного репозитория. В подключениях нескольких чатов проверяй или явно выбирай авторизацию каждой операции, не выводя токены.
4. Если прямой доступ подтверждён, работай в локальной `dev`, связанной с `dev` **исходного репозитория**. Сначала проверь чистоту рабочего дерева и исходящие коммиты, выполни `git fetch origin`, затем `git switch dev` и `git pull --ff-only origin dev`. Если локальной `dev` нет, используй `git switch --track origin/dev`. В этих командах origin должен быть исходным репозиторием; если origin — fork, используй проверенный remote исходного репозитория, например upstream, и не меняй remotes вслепую. Вноси изменения, проверяй и коммить прямо в `dev`, затем отправляй в ту же удалённую `dev`.
5. Команде не создавай личные ветки, ветки задач, AI-сессий и экспериментов; PR в `dev` не является обычным этапом её работы. Внешний участник без прямого доступа использует fork, одну постоянную ветку `<github-login>` и PR в исходную `dev`. Существующую удалённую личную ветку нужно получать через tracking branch и синхронизировать обычным merge; создавать заново от dev её нельзя. Временная локальная ветка/worktree допустима только при реальной необходимости и не публикуется автоматически.
6. Не переключай ветки при несохранённой работе и не переноси старые личные коммиты в общую `dev` вслепую. Сначала сохрани и разбери их назначение. При расхождении локальной и удалённой `dev` изучи различия, объедини изменения обычным merge, разреши конфликты и повтори проверки. Не используй rebase, force push, reset --hard или удаление чужой работы для синхронизации. Несколько агентов не должны одновременно менять одну локальную рабочую копию: согласуй их работу, сохраняя общую удалённую `dev`.

## Что хранить в Git

- Исходный код, необходимые конфигурации без секретов, manifests и lock-файлы зависимостей, поддерживаемые тесты и обезличенные fixtures.
- Готовые, проверенные и используемые сайтом ассеты в каталоге проекта, например `public/assets/` или `src/assets/`. Временные варианты туда не класть.
- Итоговую документацию проекта и командные инструкции: README.md, AGENTS.md, CONTRIBUTING.md и регламент владельца.

## Что оставлять локально

- Секреты, `.env`, токены, ключи, реальные клиентские данные, выгрузки баз и приватные документы. Чувствительные материалы по возможности держи вообще вне репозитория; внутри — только в игнорируемом локальном каталоге. `.env.example` содержит только пустые или вымышленные значения.
- Брейншторминг, планы AI, логи диалогов, промежуточные отчёты, промпты и служебные артефакты нейронок. Храни их в `work/`, `.ai/` или `artifacts/`, а не в отслеживаемой документации. Не коммить `docs/superpowers/`.
- Пробные картинки, скриншоты проверок, варианты генераций, исходные загрузки и временные экспорты — в игнорируемых каталогах. В Git переносится только выбранный готовый ассет; не игнорируй все PNG/JPG/SVG целиком.
- Зависимости, сборки, кэши, временные файлы, локальные настройки IDE, локальные worktree.

До создания локального артефакта выбери игнорируемый путь. При новом типе мусора дополни .gitignore точным правилом. Не скрывай исходники, тесты, конфигурацию или готовые ассеты общим шаблоном.

`.gitignore` не защищает секреты и не исключает уже отслеживаемые файлы. Проверь `git ls-files -- <path>` и `git check-ignore -v --no-index -- <path>`. Если файл уже отслеживается, обсуди снятие с учёта через `git rm --cached -- <точный путь>`; не удаляй локальные данные и не переписывай историю самостоятельно. При утечке секрета останови push, сообщи владельцу: секрет нужно отозвать/заменить, одного gitignore недостаточно. Не цитируй секрет в отчётах.

## Перед каждым push

1. Проверь `git status --short --untracked-files=all`, `git diff`, `git diff --cached`, `git diff --check` и список файлов всех исходящих коммитов. Для команды используй `git diff --name-status origin/dev...HEAD`; для внешнего участника — `origin/<github-login>...HEAD`, если ветка существует. Убедись, что нет мусора, секретов и файлов вне задачи. Gitignore не отменяет проверки содержимого.
2. Добавляй файлы явно по путям. Не используй без разбора `git add .`, `git add -A` и `git add -f`.
3. Непосредственно перед push команды выполни `git fetch origin` и `git merge origin/dev` из локальной `dev`, повтори проверки итоговой версии. Если push отклонён, потому что другой разработчик уже обновил dev, снова fetch → обычный merge → разрешение конфликтов → проверки → обычный push. Не обходи отказ force push. Внешний участник аналогично синхронизирует свою постоянную ветку и свежую dev исходного репозитория. Не выдумывай успешные тесты, если приложения и CI ещё нет.
4. Проверь `git branch -vv` и `git worktree list`. Убери только свои временные worktree и локальные ветки, чья работа уже сохранена и полностью влита. Перед удалением проверь status, включая untracked и ignored файлы, outgoing commits и предназначение worktree. При любой несохранённой работе или неясности оставь их и сообщи человеку. Не удаляй чужие ресурсы, постоянную пользовательскую ветку, dev или master.
5. Для подтверждённо ненужного чистого worktree используй обычный `git worktree remove <точный путь>`, без force. Для влитой временной ветки — `git branch -d <имя>`. Отказ команды — причина остановиться, не повод добавлять force. Не используй `git clean`, `reset --hard`, `branch -D`, `worktree remove --force`, массовые удаления и стирание папок worktree вручную.
6. Посмотри ветки на origin (`git ls-remote --heads origin`). Не удаляй удалённые ветки без отдельного разрешения владельца и не трогай чужие. Лишние старые ветки перечисли человеку. Не используй push --all, --mirror или --tags.
7. Команда отправляет только `git push origin dev` из локальной `dev` (либо явно выбранный remote исходного репозитория). Внешний участник отправляет только свою постоянную ветку: `git push -u origin <github-login>`, затем создаёт PR. Не используй push --all/--mirror/--tags, не пушь из временной локальной ветки и не меняй master напрямую. Force push и удаление dev/master запрещены всем без исключений.

## Завершение

Для команды задача завершена после успешного push проверенных коммитов в исходную `dev`, повторного fetch и проверки, что локальная `dev` синхронизирована с удалённой. Оставайся в `dev`; не возвращайся в личную ветку. Сообщи коммит, проверки и ограничения. Прямой push в dev не является production-выкладкой.

Для внешнего участника создай или обнови PR `<github-login> → dev`, не создавая дубликаты. Сливай только по поручению человека, при наличии прав и выполненных требованиях GitHub. Используй merge commit, без squash/rebase. После слияния не удаляй ветку пользователя: обнови чистую локальную dev через pull --ff-only от исходного репозитория, затем вернись в постоянную ветку, влей свежую dev и при необходимости запушь её. На другом устройстве сначала синхронизируй рабочую ветку. Незавершённые изменения сохраняй, а не стирай ради переключения. Старые личные ветки команды без отдельного разрешения не удаляй.

Настройки доступа и защиты, теги, GitHub Releases, master и деплой меняются только по отдельному явному поручению владельца. PR в dev не является разрешением на production.

Обновление `master` разрешено только владельцу через PR из `dev`. При подключении выкладки настрой environment `production` только для `master`, с подтверждением владельца и выключенным обходом для администраторов. Не подтверждай production-запуск без отдельного поручения владельца на выпуск.
