# Порядок разработки

## Одна ветка на пользователя

У каждого разработчика одна постоянная рабочая ветка, названная его GitHub-логином: например `ivan`. Все задачи и AI-сессии выполняются в ней. Ветки на каждую задачу не создаём и ветку после слияния не удаляем. `dev` — общая разработка, `master` — production.

Без приглашения сделайте fork, работайте в своей ветке и присылайте PR в dev исходного репозитория. Принимать его будет владелец/участник с записью. Если есть доступ на запись, ваша ветка может находиться непосредственно в исходном репозитории. Общий корпоративный аккаунт разработчикам не выдаётся.

## Перед началом работы

На чистой рабочей копии проверьте `git status`, remotes, ветки и worktree. Для обычного клона origin — исходный репозиторий; для fork origin — ваша копия, upstream — исходный репозиторий (добавляется один раз по его URL).

```bash
git fetch origin
# Только для fork, если upstream настроен:
git fetch upstream
```

Если `your-login` уже есть локально, переключитесь на неё и влейте `origin/your-login` обычным merge, когда удалённая ветка существует. На новом устройстве, если ветка уже есть на сервере:

```bash
git switch --track origin/your-login
```

Только если пользовательской ветки нет ни локально, ни на origin, создайте её один раз:

```bash
git switch -c your-login origin/dev
# Для fork вместо origin/dev используйте upstream/dev.
```

Затем, находясь в своей ветке, влейте свежий `origin/dev` (`upstream/dev` для fork) обычным `git merge`. Разрешите конфликты, сохраняя работу других людей. При незакоммиченных изменениях не выполняйте команды переключения вслепую: сначала сохраните работу и разберитесь с состоянием.

## Что отправляем на GitHub

Исходники сайта, необходимые конфигурации без секретов, manifests и lock-файлы, поддерживаемые тесты, итоговую документацию и **готовые используемые ассеты**. Например, выбранная картинка для сайта идёт в `public/assets/`, а десять тестовых вариантов — в локальный `work/`.

Не отправляем секреты и .env, данные клиентов, базы и выгрузки, тестовые картинки, скриншоты проверок, промежуточные генерации, результаты брейншторминга, планы и артефакты AI, зависимости, сборки, кэши и локальные worktree. Для этого есть игнорируемые `work/`, `scratch/`, `.ai/`, `artifacts/` и другие каталоги из .gitignore. Итоговые готовые ассеты не исключаем по расширению.

`.gitignore` не убирает файлы из уже существующих коммитов и не является защитой секрета. При обнаружении отслеживаемых чувствительных данных остановите публикацию и сообщите владельцу. `.env.example` может содержать только пустые или вымышленные значения.

## Перед каждым push

1. Получите свежие изменения своей ветки с origin и dev исходного репозитория, влейте их в свою ветку обычным merge. Проверьте итог.
2. Проверьте `git status --short --untracked-files=all`, `git diff`, `git diff --cached`, `git diff --check` и список файлов исходящих коммитов. Добавляйте конкретные нужные файлы, а не всё через git add . / -A. Не используйте add -f.
3. Просмотрите `git branch -vv`, `git worktree list` и `git ls-remote --heads origin`. После проверки уберите только свои временные worktree без несохранённых данных и влитые ненужные локальные ветки. Используйте обычные worktree remove и branch -d, без force. При сомнении оставьте и сообщите человеку. Удалённые ветки удаляются только с отдельного разрешения владельца.
4. Запустите доступные проверки приложения. Пока приложения и сборки нет, явно укажите это в PR.
5. Создайте осмысленные коммиты и отправьте **только свою постоянную ветку**:

```bash
git push -u origin your-login
```

Не используйте push --all, --mirror, --tags или --force. Не удаляйте чужие ветки, dev/master, свою постоянную ветку и несохранённые файлы. Не используйте git clean/reset --hard для «уборки».

## PR и продолжение работы

Создайте либо обновите существующий PR `your-login → dev` исходного репозитория. Укажите результат, реальные проверки и ограничения. Если dev изменился, снова влейте его и перепроверьте работу. Слияние выполняется **merge commit**, без squash/rebase, чтобы постоянная ветка сохраняла общую историю с dev.

После слияния обновите чистую локальную dev через `git pull --ff-only origin dev` (для fork — `upstream dev`) и проверьте общую версию. Вернитесь в свою постоянную ветку, влейте обновлённый dev и при необходимости запушьте её. Следующая задача продолжится в этой же ветке. На другом устройстве сначала синхронизируйте её с origin.

## Production

Только владелец сливает PR dev → master и выполняет релизы/выкладку по отдельной процедуре. Автоматического деплоя в шаблоне нет.
