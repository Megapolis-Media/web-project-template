# Порядок разработки

## Доступ

Есть два варианта:

1. **Без приглашения:** сделайте fork, создайте рабочую ветку в нём и пришлите PR в `dev` исходного репозитория. Слияние выполняет владелец или приглашённый участник с правом записи.
2. **С доступом на запись:** создавайте рабочие ветки в исходном репозитории. Можно самостоятельно сливать PR в `dev`, если выполнены правила GitHub и владелец разрешил этот процесс. `master` остаётся доступной для обновлений только администратору.

Публичность не даёт права записи. Не используйте общий корпоративный аккаунт для разработки.

## Начало задачи

Для участника с доступом на запись, на чистой рабочей копии:

```bash
git status
git fetch origin
git switch -c your-login/task-name origin/dev
```

Для fork: `origin` — ваша копия; `upstream` — исходный репозиторий. Один раз добавьте upstream по URL проекта, затем:

```bash
git status
git fetch upstream
git switch -c your-login/task-name upstream/dev
```

Если рабочая ветка уже существует, переключитесь на неё и влейте свежую удалённую `dev`. Не создавайте её заново поверх имеющейся работы.

## Перед отправкой

Получите свежий `dev` исходного репозитория, влейте его в рабочую ветку и повторите проверки:

```bash
git fetch origin
git merge origin/dev
# Для fork вместо origin используйте upstream в двух командах выше.
# Выполните доступные проверки сборки, тесты и ручную проверку задачи.
git diff --check
git status
# Добавьте только нужные файлы, затем:
git commit -m "Describe the change"
git push -u origin your-login/task-name
```

Создайте PR с базовой веткой `dev` **исходного** репозитория. Укажите задачу, изменения, проверки и скриншоты для интерфейса. Если dev изменился после проверки, снова обновите ветку и перепроверьте её.

В текущем шаблоне нет приложения и CI. Нельзя утверждать, что сборка прошла. После выбора стека владелец добавляет реальные проверки и делает их обязательными.

## Слияние и проверка общей версии

Владелец или участник с разрешённой записью сливает PR в dev через GitHub. На чистой рабочей копии обновите локальную dev через `git pull --ff-only origin dev`; для fork используйте `upstream dev`. Затем повторите применимые проверки. Не делайте обычный `git push origin dev`.

## Production

Владелец создаёт PR `dev → master`, проверяет итоговый diff и выполняет слияние. Автоматического деплоя нет. Теги и выкладку выполняет владелец по отдельной процедуре.

Запрещены секреты в коммитах, force push в общие ветки, изменения чужих веток, самостоятельный выпуск в production и обход правил доступа.
