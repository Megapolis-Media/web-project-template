# Порядок разработки

## Одна общая dev для команды

Команда разработки работает прямо в одной удалённой ветке `dev` исходного репозитория. Получить свежую dev → внести изменения → проверить → закоммитить → снова синхронизировать dev → отправить в ту же dev. Личные ветки и PR в dev команде не нужны. `master` используется только для production-выпуска владельцем.

Для прямого доступа участнику нужно принять приглашение Write и получить персональное исключение из обязательного PR в действующем ruleset. Каждый разработчик работает под своим аккаунтом. Если прямого доступа нет, используйте процесс через fork и PR, описанный ниже. При работе над самим шаблоном проверяйте доступ и правила в репозитории шаблона.

## Перед началом работы

### 1. Проверить рабочую копию и получить dev

Проверьте `git status`, `git remote -v`, `git branch -vv`, `git worktree list` и GitHub-аккаунт. Перед переключением сохраните и разберите незавершённую работу и старые исходящие коммиты; не удаляйте их и не переносите в общую ветку вслепую. Несколько агентов не должны одновременно редактировать одну локальную рабочую копию.

В командах ниже `origin` указывает на исходный репозиторий проекта. Если `origin` указывает на fork, используйте проверенный remote исходного репозитория, например `upstream`. Не меняйте remotes вслепую.

```bash
git fetch origin
git switch dev
git pull --ff-only origin dev
```

Если локальной dev ещё нет, вместо `git switch dev` выполните `git switch --track origin/dev`. Если pull --ff-only отклонён из-за расхождения истории, изучите различия и объедините их обычным merge, сохраняя работу других людей. Не используйте rebase, reset --hard или force push для синхронизации общей dev.

### 2. Внести изменения, проверить и закоммитить в dev

Редактируйте файлы прямо в локальной `dev`. Выполните проверки, соответствующие изменению. Просмотрите diff и добавьте только конкретные файлы задачи; не используйте git add . / -A / -f. Создайте осмысленный коммит в этой же ветке.

### 3. Учесть параллельную работу и отправить в ту же dev

Непосредственно перед отправкой получите чужие коммиты:

```bash
git fetch origin
git merge origin/dev
```

Разрешите конфликты и повторите проверки итоговой версии. Затем:

```bash
git push origin dev
```

Если push отклонён, потому что dev уже обновил другой разработчик, повторите fetch → merge → разрешение конфликтов → проверки → обычный push. Не обходите отказ force push. После отправки выполните fetch, проверьте `git status --short --branch` и синхронизацию с origin/dev. Продолжайте следующую задачу в dev, а не в личной ветке.

## Внешние участники без прямого доступа

Сделайте fork. Используйте одну постоянную ветку `<github-login>` и PR в dev исходного репозитория; ветки на каждую задачу не создавайте. Если ветка уже есть на сервере, получите её через `git switch --track origin/<github-login>`, а не создавайте заново от dev. Сначала синхронизируйте её с origin и обычным merge влейте свежую dev исходного репозитория (обычно upstream/dev). Если ветки нигде нет, создайте её один раз от свежей исходной dev. Затем проверки → commit → повторная синхронизация → `git push -u origin <github-login>` → PR. Уже существующие личные ветки команды без отдельного разрешения не удаляются.

## Что отправляем на GitHub

Исходники сайта, необходимые конфигурации без секретов, manifests и lock-файлы, поддерживаемые тесты, итоговую документацию и **готовые используемые ассеты**. Например, выбранная картинка для сайта идёт в `public/assets/`, а десять тестовых вариантов — в локальный `work/`.

Не отправляем секреты и .env, данные клиентов, базы и выгрузки, тестовые картинки, скриншоты проверок, промежуточные генерации, результаты брейншторминга, планы и артефакты AI, зависимости, сборки, кэши и локальные worktree. Для этого есть игнорируемые `work/`, `scratch/`, `.ai/`, `artifacts/` и другие каталоги из .gitignore. Итоговые готовые ассеты не исключаем по расширению.

`.gitignore` не убирает файлы из уже существующих коммитов и не является защитой секрета. При обнаружении отслеживаемых чувствительных данных остановите публикацию и сообщите владельцу. `.env.example` может содержать только пустые или вымышленные значения.

## Перед каждым push

1. Команда в dev получает свежую origin/dev и объединяет изменения обычным merge. Внешний участник синхронизирует свою постоянную ветку и исходную dev. После объединения проверьте итог.
2. Проверьте `git status --short --untracked-files=all`, `git diff`, `git diff --cached`, `git diff --check` и список файлов исходящих коммитов. Добавляйте конкретные нужные файлы, а не всё через git add . / -A. Не используйте add -f.
3. Просмотрите `git branch -vv`, `git worktree list` и `git ls-remote --heads origin`. После проверки уберите только свои временные worktree без несохранённых данных и влитые ненужные локальные ветки. Используйте обычные worktree remove и branch -d, без force. При сомнении оставьте и сообщите человеку. Удалённые ветки удаляются только с отдельного разрешения владельца.
4. Запустите доступные проверки, соответствующие изменению. Не заявляйте об успешных проверках, которые не выполнялись.
5. Команда коммитит и отправляет только общую dev; внешний участник — только свою постоянную ветку:

```bash
git push origin dev
# Только для внешнего участника в его fork:
git push -u origin your-login
```

Не используйте push --all, --mirror, --tags или --force. Не удаляйте чужие ветки, dev/master, свою постоянную ветку и несохранённые файлы. Не используйте git clean/reset --hard для «уборки».

## Завершение работы и PR внешних участников

Для команды завершение — успешный push в dev, проверка синхронизации и сообщение о коммитах, реальных проверках и ограничениях. PR в dev не создаётся, личная ветка не нужна; следующая задача также начинается с обновления dev.

Внешний участник создаёт либо обновляет один PR `your-login → dev`. Слияние выполняется merge commit, без squash/rebase. После слияния он сохраняет личную ветку, получает исходную dev, возвращается в свою постоянную ветку, вливает обновлённую dev и при необходимости отправляет обычным push. Перед работой на другом устройстве также нужно синхронизировать рабочую ветку.

## Production

Только владелец сливает PR `dev → master`. Прямой push в `master` запрещён. При подключении выкладки настройте workflow только для `master` и обязательное подтверждение владельца в environment `production`. [Регламент владельца](docs/MAINTAINERS.md)

Подробные обязательные проверки для нейронки: [AGENTS.md](AGENTS.md).
