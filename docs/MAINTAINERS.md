# Регламент владельца

## Новый проект из шаблона

Владелец с установленными GitHub CLI и PowerShell запускает:

```powershell
./tools/New-WebRepository.ps1 -Owner Megapolis-Media -Name my-website -Template Megapolis-Media/web-project-template
```

Команда создаёт **публичный** репозиторий из одной ветки шаблона, создаёт вторую ветку с общей историей и применяет настройки защиты. Если репозиторий уже существует, команда останавливается. После сбоя возможен частично настроенный репозиторий: проверьте его перед выдачей доступа.

При использовании кнопки **Use this template** выбирайте только одну ветку, затем вручную настройте общую историю веток и защиту. Файлы шаблона сами по себе не переносят настройки доступа и rulesets.

## Границы настройки

- Нет приложения, сборки, CI, хостинга и доступа к серверу. Проверки и required status checks добавляются вместе с реальным стеком проекта.
- Нет ключей, паролей, `.env`, данных клиентов и прав на материалы заказчика. Публикуйте только то, что разрешено раскрывать.
- Теги может создавать и изменять только администратор. Стандартное право записи не позволяет полностью запретить работу с GitHub Releases: не используйте Releases как разрешение на деплой.
- Администраторы управляют доступом. Разработчики не получают корпоративный токен.
- Код сайта и клиентские материалы не получают открытую лицензию автоматически. Публичность репозитория не заменяет согласование прав.

## Настройки каждого нового репозитория

- Public; default branch `dev`; связанные ветки `master` и `dev`.
- Обе ветки: обязательный PR, разрешён только merge commit, без обязательного review; запрещены force push и удаление. Нет обхода этих правил даже администратором.
- `master`: отдельное ограничение обновления, обход только для repository admin. Оно не отменяет обязательный PR из общего ruleset.
- Все теги: создание, обновление и удаление только repository admin. Не выдавайте права администратора разработчикам.
- Автоматическое удаление слитых веток выключено: у каждого пользователя одна постоянная ветка с именем его GitHub-логина. Ветки на задачи на сервере не создаются. dev/master — системные ветки. Это правило регламента; текущие rulesets не ограничивают количество или владельца рабочих веток.
- GitHub Actions выключены на этапе пустого шаблона. Перед включением настройте безопасный CI, минимальные разрешения и обязательные status checks. Не запускайте недоверенный код fork с секретами через pull_request_target.
- Никаких приглашений, серверных ключей, webhooks и deploy credentials первоначальная настройка не создаёт.

`tools/New-WebRepository.ps1` применяет эти настройки к новому проекту. Просмотрите Rulesets и права после запуска. Никогда не объявляйте проект защищённым только потому, что файлы шаблона скопированы.

## Релизы и деплой

На стандартных ролях GitHub право записи включает управление Releases. Правила тегов ограничивают выпуск новых тегов, но не заменяют отдельный запрет редактирования Releases на уже существующих тегах. Полный запрет не обещаем.

Не подключайте production к произвольному событию release, tag или workflow из рабочей ветки. Для будущего деплоя допускайте только master, настройте production environment с разрешённой веткой и ручным подтверждением владельца. Проверяйте доступность этих функций на текущем тарифе. Production secrets храните только в защищённой среде или во внешней системе выкладки под контролем владельца.

## Приёмка изменений

1. Для PR из fork проверьте автора, diff, лицензии и отсутствие секретов. Не исполняйте неизвестный код с корпоративными ключами.
2. До слияния проверьте изменения относительно свежего dev. После слияния проверьте общую версию.
3. Для выпуска создайте PR dev → master. Проверяйте, что head — dev этого репозитория. GitHub не ограничивает источник PR одними настройками данного шаблона.
4. Теги и публикации выполняет владелец после проверки. Факт GitHub Release не является разрешением на деплой.

Изменения шаблона не распространяются в уже созданные проекты автоматически. Настройки rulesets и документацию обновляйте отдельно и проверяйте.
